## 1. 共同设计

| 实验 | 每个 arena 的内容 | 主测规模 `num_envs` |
| --- | --- | --- |
| L-02 基础物体 | 一个立方体或一个球，分开测 | 1、100、1000 |
| L-03 机器人 | 一台完整机器人，机器人种类分开测 | 1、100、1000 |
| L-04 工作站 | 一套完整工作站，含机器人、工作台和任务物体 | 1、16、64；容量再扩大 |
| L-05 工作间 | 一间完整工作间，含家具、机器人和物件 | 1、4、16；容量再扩大 |

N=1 只用于观察固定启动成本。每环境内容固定后再扫描 N；每环境物体数、N、总物体数分别保存。L-04／L-05 的小规模起点由单场景复杂度决定，仍必须测多环境，不能只交付单场景结果。

EmbodiChain 使用 `SimulationManagerCfg(num_envs=N)`；Isaac Lab 使用 `InteractiveSceneCfg(num_envs=N, replicate_physics=True, filter_collisions=True)`。通过各自原生复制机制创建 arena，保留正常的资产共享和物理复制优化。禁止用一个 env 中 N 个对象、循环 N 次单 env world 或只复制 visual 代替。异构场景是**每个 arena 内部**有多种资产，arena 之间复制同一模板。

两平台引用相同源文件及依赖，离线准备并记录 SHA-256、许可、字节数。无运行时下载。质量、惯量、碰撞、关节、初态等必须对齐；不能一端删 link、降面数或改碰撞。提前转换只针对资产，不将一端完整预制场景与另一端从零构造混比。硬件、提交及导入模块路径按每次实测保存，不自动切换旧版本。

## 2. 运行及计时

主测无窗口、无相机、关闭渲染，不运行 RL、规划、控制器或任务观测。关闭重力，物理步长 5 ms；通过首个物理步及全部环境状态读回来确认可以开始仿真。平台原生初始化内置步也计入成本并注明。

| 指标 | 边界及用途 |
| --- | --- |
| `T_engine` | Python 入口至仿真管理器初始化完成，含导入和运行时启动 |
| `T_declare` | 引擎初始化后至场景声明／原生克隆完成；各平台内部边界不同，不将该阶段当纯解析速度比 |
| `T_prepare` | 声明后至物理模型准备与 GPU 同步完成 |
| `T_ready` | 入口至首步、GPU 同步、**全部环境**状态读回完成，主比较指标 |
| RAM／VRAM 峰值 | 外部 20 ms 采样，统计入口至 ready；全进程生命周期峰值另列 |
| 单位环境成本 | `T_ready/N`、内存/N，连同总成本展示；不是稳态物理 FPS |
| 规模边界 | 各 N 完成次数、超时阶段、OOM 或其他错误，不把未测点或超时预算当引擎绝对容量 |

进程级 GPU 内存优先同时读取计算和图形进程；保留采样原文、整卡占用及其他计算进程。各平台顺序运行，交替先后次序；有其他 GPU 计算任务时等待。测量截止、审计、录像及退出分别记录。180 s 是单进程预算，包含计时后的审计和退出；即使准备完成也须区分审计超时，不能混称加载失败。

C/H 均为新进程，保留 OS 文件缓存、通用 shader/kernel 缓存；能隔离的场景缓存明确记录。H 先完成一次同配置预载，再做独立重复。解析碰撞无需 mesh cooking 时，C/H 不代表两种真正不同的碰撞缓存状态，不对其差异强行作缓存收益解释。不得写成磁盘冷启动。

L-04 的 B（同进程销毁重建）覆盖全部 N 个 arena，报告销毁、重建及合计；R（状态重置）对所有 arena 的刚体、关节和驱动目标执行统一扰动及恢复，恢复后逐环境读回。不同平台无法保留同样的应用组件时分别说明，不能等同于纯资产加载。

## 3. L-02：基础场景并行加载

每个 arena 一个 50 mm 立方体或直径 50 mm 球，质量 0.1 kg，局部位置 `(0,0,0.1)` m。visual 为文件 mesh（立方体 12、球 528 个三角形），碰撞分别为解析 box／sphere。使用已生成的 `cube_S.usda`、`sphere_S.usda`，物理属性随源文件导入。两平台 arena 间距均为 0.2 m；各自原生 origin 排列可不同，状态必须转换至局部坐标比较。

仅声明一份物体配置，通过 `num_envs` 创建实例。底层可能存在平台自动地面或静态节点，单列实际数量，不将其冒充动态物体。每次必须读回 N 个动态刚体，状态形状为 `(N,1,13)`。

主矩阵：两形状 × N=1／100／1000 × C/H × 两平台，每格 3 次；立方体 N=1000 的 C/H 每格 10 次，共 100 次主测。H 的额外预载不计入重复数。先做 N=4 功能预检，再做 N=100／1000 的规模预检；任何失败保留日志，修正脚本后使用新标签。

容量：共享立方体从 N=2000、4000、8000、16000 递增，各平台独立，H 预载一次并测 3 次。低规模失败后停止该平台更高点，保留原因；必要时在相邻成功／失败点之间补测。测试上限仍完成时只报告“已测至 16000”，不称极限。

旧 S/U 对照通过一个 arena 内不同对象构成，不能直接搬成并行环境数量。当前采用同模板多 arena 的 S 组，不计算 `T_U/T_S` 或声称已评估异构 arena；异构内容的复制由 L-05 覆盖。若后续增加逐环境不同资产，须先验证两边公共 API 及复制语义，另立配置，不能以 N 个对象替代。

当前实现使用 `protocol-v3-multi-arena.json`；**L-02 的 EmbodiChain 主配置为 `rigid_enable_sleep=False`**，由用户于 2026-10-27 指定。当前三章报告（原数据工作区：`outputs/benchmarks/L-02/sleep-off-main-v1/reports/L-02.md`）引用 `sleep-off-v1/` 的原始容量数据，关闭睡眠的补录视频位于 `sleep-off-main-v1/`。调用入口显式传 `--sleep off --platforms embodichain --output-root <新目录>`，并核验实际睡眠对象未构造。Isaac 保留原 PhysX 配置，不宣称两端睡眠策略相同。主测关闭渲染，不与旧协议的首帧耗时计算加速比。

本轮执行发现：当前冻结 DexUni 的 VBD 睡眠邻接表受总刚体数限制，2896 单刚体 arena 可加载，2897 报错；证据与复测要求（原数据工作区：`outputs/benchmarks/L-02/multi-arena-v1/reports/release-review.md`）。后续先核对实际求解分支，再查 `model.body_count`；L-03 当前纯关节预检未构造 VBD，该上限不直接适用。L-04／L-05 含独立刚体时仍需核验，不能为继续大矩阵擅自关闭睡眠；限制按版本和分支跟踪。

关闭睡眠已验证 N=1000／4000／8000 各 3 次容量重复完成；16000 在共享 GPU 下未于预算内就绪，不据此判定上限。当前缺少关闭睡眠的独占 GPU 主矩阵、球体规模扫描及容量性能；按上述矩阵补测时使用新 tag 和输出目录，不续跑已停止的旧计划。旧 `multi-arena-v1/` 的 EmbodiChain 时间、内存和倍率仅属于 sleep 开启配置，不能搬入本版。共享 GPU 观测保留原值及资源条件，不纳入公平排名。睡眠配置选择仅适用本项，不自动修改其他实验。

## 5. L-04：完整工作站并行加载

每 arena 公共内容：一台 Franka、一张 1.6×1.0 m 工作台、托盘和地面。台高 0.75 m，机器人局部基座 `(0.15,0.5,0.75)` m，使用冻结的准备姿态；arena 间距至少 3 m。主测不添加观察相机，录像另加。

| 模板 | 每 arena 的附加内容 |
| --- | --- |
| W20 | 20 个动态刚体，cube／cylinder 各半，最大 50 mm，5×4 槽位 |
| W100 | 100 个动态刚体，cube／cylinder 各半，10×10 槽位 |
| WD | 一套 SlidingBoxDrawer，保留滑轨和关闭初态 |
| WI | 直径 20 mm、长 50 mm 的销及带开孔底座，径向间隙 1 mm，初始分离 |

W100 槽位为 `(0.55+0.08i,0.14+0.08j)` m，i/j=0…9；W20 取固定子集。种子 0 生成 ±5 mm、±5° 扰动后冻结，两端共用；先排除初始穿透。插接孔使用相同凸分块，不能用封孔的整体凸包。

每模板 × N=1／16／64 × C/H/B/R，各 3 次。W100、N=64 每模式 10 次作为典型点；更大规模按 128、256、512 递增探测。第二 GPU 只有实际可用时复测 W100、N=64 并单列，不能标为已完成。shader 全冷与有相机加载仅作另列诊断，不混入物理就绪曲线。

R：全部环境刚体平移 10 mm、线／角速度各 0.1 m/s／rad/s；关节偏移 0.05 rad 或 10 mm，向限位内扰动，驱动目标同改。恢复并同步后保存逐环境逐对象残差，另记首步后跳变量。另做 W100、N=64 连续 10 次 B 和 100 次 R，检查内存趋势，不把同进程次数当独立样本。

2026-10-27 执行记录：WD 的 SlidingBoxDrawer 源资产已找到并离线转换，但 N=1／4 的共同 USD 预检发现 EmbodiChain 抽屉碰撞为 0、Isaac 为 2；父级 Xform 碰撞属性解析问题与 G1 一致。转换还合并了源 OBJ 的 28 个凸分块。正式矩阵暂停，先处理共同输入／导入适配；W20／W100／WI 尚未运行，不推断其存在相同问题。证据和恢复条件见 L-04 资产预检（原数据工作区：`outputs/benchmarks/L-04/reports/L-04.md`）。原始输入保留，不把内存中的定位试验当作已修复。

## 6. L-05：异构工作间并行加载

每 arena 复制完整 8×6×3 m 工作间：地面、三面墙、两张工作台、四个柜、两套五层货架及一台 Franka，arena 间距至少 10 m。背景全部有碰撞且静态。物件最大 150 mm，槽位间留至少 10 mm 间隙；冻结布局后核验是否实际放得下，不以计划尺寸代替几何核验。

S100／S1000：每房间 100／1000 件物体引用同一箱体 mesh、材质及 1024×1024 贴图。U100／U1000：每房间由盒、瓶、杯、托盘、工具各 4 种共 20 个资产组成，五类等比例，保留各自 visual、碰撞和贴图；物体数量增大不增加资产种类。每组 20% 动态、80% 静态，动态质量 0.1 kg，惯量按几何计算。背景及机器人不计入这 100／1000 件。

每模板扫描 N=1／4／16 的 C/H，各 3 次；U1000、N=16 每模式 10 次。S100 容量按 N=32／64／128 试探。每个 arena 内含异构资产，但所有 arena 的模板相同，保留可用的物理复制优化。

主表同时列 `num_envs`、每环境物体数、总物体数和唯一源资产数。S/U 的差异含场景内容差异，不能解释成纯缓存收益。关闭物理的 visual-only 诊断可另测，不代替多 arena 主测。

## 7. 预检、证据和交付

1. 核对公共 API 是否真的创建 N 个 arena；保存 arena 标识、origin、实例数、逐环境对象／关节数及状态形状。全量状态有限且输入一致后才开始主测。
2. N=4 时把 arena 0 的物体放到与 arena 1 物体在世界坐标中重叠的位置，推进若干步，检查是否产生跨环境碰撞响应；保存操作前、写入后、连续状态。该诊断不计入加载时间。机器人／工作站沿用等价隔离检查。

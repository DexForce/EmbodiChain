Action Agent Pipeline Architecture
==================================

Dependency direction
--------------------

The package follows this dependency direction:

    config / protocol / domain
                |
                v
        generation / runtime
                |
                v
         agents / env_adapters
                |
                v
                 cli

The generation and runtime layers are peers. They must not import each other.
Shared serialized values belong to protocol, shared object classification
knowledge belongs to domain, and tunable or numeric fallback policy belongs to
config.

Canonical imports
-----------------

Production modules import constants from their owning modules, for example:

    protocol.artifacts
    protocol.actions
    protocol.tasks
    protocol.success
    domain.object_semantics
    generation.relation_language
    config.defaults

This keeps each dependency narrow and makes ownership visible at the import
site.

Static dependency visibility
----------------------------

Package-internal dependencies must be recoverable from source without executing
production code. Architecture tests resolve absolute imports, relative imports,
parent-package submodule imports, and dynamic imports whose target is a string
literal. The same normalized dependency set drives layer, compatibility facade,
canonical owner, and cycle checks.

Non-literal dynamic imports are prohibited because variable, configured, or
constructed module names make the static dependency graph unverifiable. A
future plugin loader must live behind a documented boundary with a narrow,
explicit architecture-test exemption rather than weakening this package-wide
rule.

Test placement
--------------

Action-agent tests live under tests/gen_sim/action_agent_pipeline, matching the
repository-wide pytest layout. The production package must not contain its own
tests package; this keeps architecture checks in the default CI test run and
prevents test modules from being included in distributable Python packages.

Compatibility facades
---------------------

The root contracts.py, semantics.py, and defaults.py modules preserve public
imports used by external callers and recorded tooling. They contain explicit
re-exports only and are not canonical dependencies for production modules.
The env_adapters/tableware/success.py module serves the same purpose for the
historical success-evaluator path.

Compatibility aliases have no scheduled removal. New production code must not
import through a facade, and architecture tests enforce this rule.

Orientation policy ownership
----------------------------

The domain.orientation_policy module is the canonical owner of principal-axis
ordering, upright and lay-flat target rotations, and generation-time rotated
z-min prediction. Generation and runtime modules may adapt mesh data to their
own representations, but they must not reimplement these policy decisions.

The generated runtime UID and ObjectSemantics.label are the shared object
identity for orientation classification. Generation-only descriptions and mesh
filenames must not change a policy decision that Runtime cannot reproduce.

Arrangement planning ownership
------------------------------

The generation.arrangement_spec module is the stable orchestration entry for
line-arrangement generation. It delegates response normalization to
generation.arrangement_intent, collision-aware slot geometry to
generation.arrangement_layout, and arm assignment plus occupancy scheduling to
generation.arrangement_execution.

These modules form a one-way dependency graph: execution may use layout
primitives, while intent, layout, and execution must not import the
arrangement_spec entry module. Moving a helper must preserve the existing
arrangement_spec import when that name is part of its compatibility surface.

Relative planning ownership
---------------------------

The generation.relative_spec module is the stable orchestration entry for
relative-manipulation specs. Semantic normalization and runtime UID resolution
belong to generation.relative_intent. Coordinated payload canonicalization,
direction, terminal behavior, and forced-arm assignment belong to
generation.relative_coordinated_spec.

Relative geometry is split by policy boundary. generation.relative_offsets
owns basic offsets, absolute self-relative targets, and final arm assignment;
generation.relative_slot_geometry owns deterministic container slots;
generation.relative_transport_geometry owns coordinated carrier motion and
side-release height; generation.relative_surface_geometry owns surface contact
and orientation-aware mesh height. These modules may depend on
generation.relative_intent and relative_offsets, but they must not import
relative_spec or the relative_geometry compatibility aggregator.

Semantic-step execution
-----------------------

Object-manipulation model output is an ordered semantic program. Generation
normalizes that program into seed_task_graph.json, which is the authoritative
symbolic artifact. A seed graph contains stable step IDs, dependencies,
symbolic goals, postconditions, and user-required arm bindings, but never
atomic edge IDs, absolute targets, trajectories, or joint states. The same seed
graph can therefore describe every environment that shares the object registry.

Deterministic route builders compile the seed graph plus generated scene
geometry into task_graph.json. The compiled graph stores seed_graph_hash and is
published in the same file transaction as its seed, preventing --overwrite
from leaving a new semantic program beside a stale executable graph.

Runtime executes semantic edge ranges in order. At each boundary it validates
dependencies and live object bindings, lets the existing atomic target
resolvers and motion planners read current simulator poses, settles physics,
and evaluates the step postcondition per environment. It must not construct a
second episode-wide grounded graph or infer reachability from arm-base
distance. Runtime continues to execute task_graph.json in this phase;
seed_task_graph.json is generation provenance, not an alternate execution
input. Environments share one semantic program while retaining independent
success and failure masks.

Config bundle ownership
-----------------------

The generation.action_agent_config module is the public generation entry and
task-route dispatcher. Route-specific bundle construction belongs to
generation.config_bundle_builders, source-scene transform ordering and
body-scale policy belong to generation.scene_transforms, shared robot and
registry helpers belong to generation.bundle_support, and mesh finalization
plus artifact writing belong to generation.bundle_finalization.

Bundle builders keep the arrangement, stacking, and relative flows explicit.
They may use scene_transforms and bundle_support, but none of these owner
modules may import action_agent_config. Compatibility aliases in the entry
module preserve established private import paths without moving ownership back
into the dispatcher.
